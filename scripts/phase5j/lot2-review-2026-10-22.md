## 1. Anomalies classées par criticité

### 🔴 CRITIQUE

**A1 — Contradiction auto-élévation : la politique `users_insert` AUTORISE la création d'un compte admin,
alors que le plan et le test I7 annoncent un refus.**
- Lignes concernées : SQL l.121-123 (`CREATE POLICY users_insert ... WITH CHECK (role IN ('user','admin') ...)`) ;
  SQL l.199-201 (test I7 : « INSERT users (role='admin') → REFUS ») ; registre §21.4 (« Register fige role='user' »)
  et §21.6 (« auto-élévation de rôle bloquée »).
- Justification : avec le credential `cvcraft_app`, un `INSERT INTO users (..., role='admin', ...)` passe le
  `WITH CHECK` (la valeur `'admin'` est dans la liste) → **création d'un compte administrateur = élévation de
  privilèges effective au niveau base**. Le plan déclare cette élévation bloquée (« contrôle majeur ») : la
  déclaration est fausse pour l'INSERT (elle n'est vraie que pour l'UPDATE — I3, via l'absence de la colonne
  `role` dans les grants). Le test I7 tel qu'écrit **échouerait** contre la politique telle qu'écrite.
- Exigence non respectée : « vérifier que les politiques ne permettent ni accès transversal non voulu ni
  auto-élévation ».
- Correction requise (décision D1) : `WITH CHECK (role = 'user')` sur `users_insert` (le runtime n'insère jamais
  `'admin'` — register force `USER_ROLES.USER`, vérifié A11 du Lot 1) **ou** maintenir la liste et réécrire I7
  en ACCEPT avec risque résiduel acté.

### 🟠 MAJEURES

**A2 — `GRANT TRIGGER` : privilège excessif avec justification techniquement fausse.**
- Lignes : SQL l.89-90 (« B8. TRIGGER : requis pour que les triggers BEFORE UPDATE existants s'exécutent sous
  ce rôle ») et SQL l.288-290 (le `GRANT TRIGGER` réel, **orphelin après C6**) ; registre l.818, 911 (R3), 958, 962.
- Justification : en PostgreSQL, le privilège `TRIGGER` est le droit de **CRÉER des triggers** sur une table —
  il n'est **pas** requis pour **déclencher** les triggers existants. `set_updated_at()` s'exécute automatiquement
  à chaque UPDATE sans privilège du rôle appelant (fonction `SECURITY INVOKER`, `prosecdef=false` mesuré, qui ne
  touche que `NEW.updated_at`, sans accès table). Conséquences : (1) la justification de B8 est fausse ; (2) ce
  GRANT est un **privilège superflu** qui autoriserait `CREATE TRIGGER` (vecteur de persistance si le credential
  est compromis) alors que B9 affirme « aucun DDL possible » — contradiction interne. Risque contenu (aucune
  fonction dangereuse dans `public`, pas de CREATE sur le schéma), mais le moindre privilège impose de retirer
  ce GRANT (D2). Le test I12 reste valide **sans** ce GRANT — à confirmer en environnement isolé.

**A3 — SQL structurellement corrompu : statement coupé + GRANT orphelin.**
- Lignes : `CREATE POLICY payments_insert` commence l.183-185 (« `WITH CHECK (amount >= 0 AND currency = 'XOF'` »
  **sans point-virgule**) et se termine l.267 (« `AND status IN (...)) ;` ») — **les sections D et E (l.187-266)
  sont intercalées AU MILIEU du statement**. Le `GRANT TRIGGER` de B8 est rejeté l.288-290 après C6, et le
  commentaire B9 se retrouve en fin de fichier (l.292-296).
- Justification : la syntaxe reste exécutable (lignes intercalées = commentaires `--` ignorés par l'analyseur),
  mais le document est **inauditable et fragile** : toute relecture ou modification ultérieure casserait le
  statement. En l'état, le fichier ne peut pas être approuvé comme script d'application (D4).

**A4 — Retour arrière incomplet et preuve insuffisante.**

### 🟡 MOYENNES

**A5 — Comptage incohérent des politiques : 15 réelles vs « 12 » annoncées.**
- Lignes : SQL = 15 `CREATE POLICY` (l.116, 121, 127, 133, 138, 143, 148, 155, 160, 164, 169, 179, 183, 274, 278
  — mesuré) ; registre §21.7 étape 3 (« `pg_policies` = 12 politiques ») et §21.11 (« 12 politiques par
  commande »). Le tableau §21.4 décrit bien **15** politiques (users 4, plans 4, subscriptions 3, payments 2,
  transactions 2) : c'est le comptage de vérification qui est faux.
- Impact : le critère de vérification de l'étape 3 induirait l'opérateur en erreur. Correction : « 15 politiques ».

**A6 — Cascade FK non testée ; le mécanisme réel est plus nuancé que « les enfants sont purgés par CASCADE ».**
- Lignes : SQL l.86 (B7), l.132 (C1), registre §21.5 (« le CASCADE enfants reste fonctionnel »).
- Justification : seuls `payments.user_id` et `subscriptions.user_id` sont en `ON DELETE CASCADE` (mesuré).
  En revanche `payments.subscription_id → subscriptions`, `transactions.payment_id → payments` et
  `subscriptions.plan_id → plans` sont en **NO ACTION** (mesuré). La suppression d'un utilisateur possédant un
  historique complet (subscription + payment + transaction) combine triggers RI en cascade ET contrôles NO ACTION
  dont l'ordre n'est pas garanti : le `DELETE FROM users` peut échouer (violation de clé étrangère) selon l'ordre
  de déclenchement. Cas actuellement latent (les paiements ne sont jamais créés : plans payants → 503, test P3
  du Lot 1), mais actif avec GeniusPay. `users_delete` est une fonctionnalité réelle (admin).
- Correction : test de cascade (matrice T9) sur environnement isolé ; correctif repository (ordre de suppression)
  si échec.

**A7 — Credential des scripts de test après bascule non tranché + dry-run V4 incompatible avec les grants par colonne.**
- Lignes : SQL l.261-263 (R4 ne couvre que `migrate`/`purge`) ; `scripts/phase5i/helpers.js` `createTestUser`
  insère `role='admin'` en SQL direct via `DATABASE_URL` ; `scripts/phase5j/pg-role-dryrun.js` V4 exécute
  `UPDATE users SET name = ...`.
- Justification : (1) après bascule de `DATABASE_URL`, les scripts du Lot 1 passent par le rôle applicatif —
  sous hypothèse D1(a) (`role='user'`), `createTestUser(role:'admin')` **échouerait** ; (2) le dry-run V0-V13,
  conçu pour l'**ancien** plan (GRANT UPDATE table-wide), exécute `UPDATE users SET name` (V4) : sous les grants
  **par colonne** du nouveau plan, V4 échouerait (colonne `name` non accordée) — le harnais de validation
  référencé est **incompatible** avec le plan qu'il doit valider. À adapter avant usage (D5, D6).

## 2. Risque TRUNCATE et grants Supabase (exigence 3)

**Mesures (SELECT uniquement)** : `anon` et `authenticated` = `rolcanlogin=false` (usage via PostgREST
uniquement) ; `service_role` = `rolcanlogin=false` **mais `rolbypassrls=true`** ; les 6 tables de `public`
donnent `ALL (arwdDxtm)` à `anon`, `authenticated`, `service_role` (§21.2 + relevé). **`pg_default_acl`**
(mesuré) : les privilèges par défaut accordent **aussi** `ALL` sur les **futures** tables à `anon`,
`authenticated`, `service_role` — tout REVOKE ignorant `ALTER DEFAULT PRIVILEGES` laisserait les nouvelles
tables exposées.

| Rôle | Risque concret | Nécessaire au fonctionnement normal | REVOKE minimal proposé (décision séparée — NON exécuté) |
|---|---|---|---|
| `anon` | `TRUNCATE` **n'est pas couvert par la RLS** (opération non par ligne) ; `DELETE`/`UPDATE` neutralisés par le default-deny RLS (sonde : 0 ligne) mais grants dormants. NOLOGIN + PostgREST n'expose pas TRUNCATE → risque **faible mais injustifié** (le backend Express n'utilise jamais `anon`). | **RIEN** | `REVOKE ALL ON TABLE users, plans, subscriptions, payments, transactions, id_map FROM anon;` + `ALTER DEFAULT PRIVILEGES ... REVOKE ALL ... FROM anon` |
| `authenticated` | Idem `anon`. | **RIEN** (API Supabase inutilisée par ce projet) | idem `authenticated` |
| `service_role` | **`BYPASSRLS` + ALL** : toute fuite de la clé `service_role` = accès complet (lecture + écriture + TRUNCATE) contournant intégralement la RLS. **Risque le plus concret de la liste.** | RIEN pour ce projet ; vérifier si des services Supabase (Realtime/Storage/Dashboard) s'appuient dessus → si non : révoquer ; si oui : limiter aux tables nécessaires | `REVOKE ALL ... FROM service_role;` sous réserve de vérification plateforme |
| Tâches admin / migration | `scripts/migrate/*`, `purge-temp-users.js` utilisent `postgres` (propriétaire) — **aucun impact** des REVOKE ci-dessus. | `postgres` conservé | aucun |
| `cvcraft_app` (cible) | Non concerné (rôle distinct créé par le plan). | §21.3 | aucun |

**Effets potentiels** : suppression de l'accès Supabase API (PostgREST) sur ces tables — sans impact pour ce
projet (le front appelle le backend Express) ; à confirmer qu'aucune fonctionnalité Realtime/Dashboard n'est
active. **Décision séparée (D3) — aucune de ces commandes n'est exécutée ici.**

## 6. Conclusion

## BLOQUÉ — CORRECTIONS REQUISES

Le plan est **bien orienté** (moindre privilège par colonne, politiques par commande sans `FOR ALL`, isolation
inter-rôles/inter-utilisateurs explicitement distinguée, `id_map` exclu, additivité jusqu'à la bascule), mais il
ne peut pas être approuvé en l'état, même pour environnement de test, tant que les corrections suivantes ne sont
pas appliquées :
1. **A1 (critique)** : fermer l'auto-élévation par INSERT (`users_insert`) ou acter explicitement le risque —
   le plan affirme aujourd'hui une protection qui n'existe pas ;
2. **A3 (majeure)** : réparer la structure du fichier SQL (statement `payments_insert` coupé, `GRANT TRIGGER`
   orphelin) ;
3. **A4 (majeure)** : corriger la procédure de rollback (`REVOKE` avant `DROP ROLE`), retirer la durée non
   prouvée, et **tester le rollback sur environnement isolé** ;
4. **A2 (majeure)** : retirer `GRANT TRIGGER` (privilège superflu, justification fausse) — D2 ;
5. **A5** : corriger le comptage (15 politiques) ; **A7/D5/D6** : trancher le credential des scripts de test et
   adapter le dry-run.

Une fois ces corrections faites et la matrice §5 exécutée avec succès sur **environnement isolé**, le plan
pourra être présenté comme `APPROUVABLE POUR ENVIRONNEMENT DE TEST`, puis évoluer vers une autorisation
d'application — sans jamais être déclaré prêt pour production sans ces tests concluants.

**Aucune modification n'a été apportée à la base** (lecture seule intégrale de cette revue) ; aucune étape
ultérieure ne sera engagée sans autorisation explicite distincte.

- **Preuve requise (A4)** : exécuter ce script une fois sur environnement isolé et en conserver la sortie ;
  aucune durée de rollback ne doit être annoncée tant que cette mesure n'existe pas.
- Persiste si seul le `DATABASE_URL` est rétabli : rôle + grants + politiques (inertes) — l'étape 1 reste
  recommandée en clôture de période de surveillance.
